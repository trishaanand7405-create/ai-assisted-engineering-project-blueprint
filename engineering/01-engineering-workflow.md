# Engineering Workflow

> **Turn product intent into a working, tested and maintainable product through disciplined engineering.**

The Engineering Workflow defines how the team moves from a prioritised Product Backlog item to a working product increment.

All four project tracks follow the same fundamental workflow, even though their technologies and implementations may differ.

---

## 1. Understand

Before building anything:

* Understand the User Story.
* Review the Acceptance Criteria.
* Clarify assumptions.
* Identify dependencies and risks.
* Confirm what "Done" means.

> **Do not start coding until the team understands what it is trying to achieve.**

---

## 2. Design

Decide how the requirement should be implemented.

Consider:

* Components
* Data flow
* Inputs and outputs
* Interfaces
* Processing logic
* Model, agent, simulation or pipeline requirements
* Testing approach

Keep the design proportional to the problem.

> **Design enough to reduce uncertainty — not enough to create unnecessary paperwork.**

---

## 3. Build

Implement the agreed solution.

The team may:

* Write code
* Configure components
* Prepare data
* Build pipelines
* Train models
* Create agents
* Develop simulations
* Integrate existing tools or services

Use AI assistance where appropriate, but the team remains responsible for the resulting implementation.

---

## 4. Test

Verify that the implementation behaves as expected.

Testing may include:

* Functional testing
* Data validation
* Model evaluation
* Pipeline validation
* Agent behaviour checks
* Simulation validation
* Integration testing

The testing approach should match the nature and risk of the product.

---

## 5. Integrate

Bring the completed work together with the existing product.

Check:

* Interfaces
* Data flow
* Dependencies
* Existing functionality
* Compatibility
* Overall behaviour

Integration should happen continuously rather than being postponed until the end.

---

## 6. Demonstrate

Show the working increment to the team and stakeholders.

The demonstration should answer:

* What did we build?
* What problem does it address?
* How does it work?
* How was it tested?
* What are its current limitations?

A working demonstration is stronger evidence than a description of intended functionality.

---

## 7. Learn and Improve

Use feedback from the demonstration and Sprint Retrospective.

The team may:

* Correct defects
* Refine requirements
* Improve the design
* Create new backlog items
* Reprioritise existing work
* Record technical debt
* Improve the engineering process

The product and engineering approach should evolve as the team learns.

---

# Engineering Workflow

```text
PRODUCT BACKLOG
       ↓
   UNDERSTAND
       ↓
      DESIGN
       ↓
      BUILD
       ↓
      TEST
       ↓
    INTEGRATE
       ↓
   DEMONSTRATE
       ↓
 LEARN & IMPROVE
       │
       └──────────────→ NEXT SPRINT
```

## AI-Assisted Engineering

AI tools may assist with:

* Understanding requirements
* Exploring solutions
* Generating code
* Debugging
* Creating tests
* Analysing data
* Generating documentation
* Reviewing implementation

However:

> **AI-generated output is not automatically correct.**

The engineering team must **review, test, validate and take responsibility** for everything incorporated into the product.

---

## Engineering Principle

> **Understand → Design → Build → Test → Integrate → Demonstrate → Improve**

This workflow applies across all project tracks.

The technology may change.

**The engineering discipline does not.**
