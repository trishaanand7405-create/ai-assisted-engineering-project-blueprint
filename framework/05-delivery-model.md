# Delivery Model

> **Deliver small, working increments that can be reviewed, tested and improved.**

The AI-Assisted Engineering Project Blueprint uses an incremental delivery model.

Teams do not attempt to build the entire product before showing it to anyone.

Instead, they progressively create and validate working increments.

---

## 1. Delivery Flow

``
BACKLOG ITEM
     ↓
UNDERSTAND
     ↓
DESIGN
     ↓
BUILD
     ↓
TEST
     ↓
INTEGRATE
     ↓
DEMONSTRATE
     ↓
FEEDBACK
     ↓
IMPROVE
```

Each completed cycle increases the product's value or confidence.

---

## 2. Small Increments

A Sprint should target a **small, meaningful increment**.

A good increment should be:

* Understandable
* Testable
* Demonstrable
* Connected to a user need
* Small enough to complete within the available time

Avoid large features that cannot be demonstrated.

> **Reduce scope before reducing quality.**

---

## 3. Evidence-Based Delivery

Teams should demonstrate evidence rather than describe intentions.

Evidence may include:

* Working application
* Test results
* Model output
* Dashboard
* Agent execution
* Simulation
* API response
* Screenshots
* Logs
* Deployment verification

The evidence should correspond to the Sprint Goal.

---

## 4. Integration

Integration should happen continuously.

Avoid waiting until the final Sprint to discover that components cannot work together.

A simple principle:

``
BUILD SMALL
    ↓
INTEGRATE EARLY
    ↓
TEST
    ↓
IMPROVE
    ↓
BUILD MORE
```

---

## 5. Quality at Delivery

Quality is not a final-stage activity.

Teams should consider quality throughout:

* Requirements
* Design
* Data
* Code
* Models
* Agent behaviour
* Testing
* Deployment
* User experience

Each increment should satisfy the applicable **Definition of Done**.

---

## 6. Release Thinking

Delivery and release are related but different.

**Delivery** creates a working increment.

**Release** makes a product version available for use.

``
WORKING INCREMENT
       ↓
VALIDATION
       ↓
RELEASE PREPARATION
       ↓
RELEASE
       ↓
USE
       ↓
FEEDBACK
```

Teams should learn to think about both.

---

## 7. Managing Incomplete Work

Not everything planned will be completed.

When this happens:

* Make the incomplete work visible.
* Preserve working functionality.
* Record remaining work.
* Reprioritise the backlog.
* Continue with the next most valuable item.

Do not hide incomplete work merely to make a Sprint appear successful.

---

## Delivery Principle

> **A small working increment creates more learning than a large unfinished plan.**

The goal of delivery is not maximum output.

The goal is **validated product value delivered continuously**.
