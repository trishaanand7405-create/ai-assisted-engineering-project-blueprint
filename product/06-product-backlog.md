# Product Backlog

> **The Product Backlog is the living, ordered list of work required to develop and improve the product.**

The Product Backlog connects the **Product Vision and Goals** to the actual work performed during Sprints.

It is **not a fixed project plan**. It evolves as the team learns more about the problem, users and product.

---

## 1. What Goes Into the Backlog?

A Product Backlog may contain:

* Epics
* User Stories
* Defects / Bugs
* Technical work
* Data or model improvements
* Security or quality work
* Maintenance activities
* Enhancements
* New requirements discovered through feedback

Not every item needs to be implemented immediately.

---

## 2. Backlog Structure

The product hierarchy can be represented as:

``
PRODUCT VISION
      │
      ▼
PRODUCT GOALS
      │
      ▼
    EPICS
      │
      ▼
USER STORIES
      │
      ├── Acceptance Criteria
      │
      └── Technical Tasks
              │
              ▼
           SPRINTS
```

The hierarchy provides structure while allowing the team to adapt as understanding improves.

---

## 3. Prioritisation

The Product Owner is accountable for backlog priority.

When deciding what should come next, consider:

* User value
* Product Goal contribution
* Business or operational importance
* Risk
* Dependencies
* Technical feasibility
* Learning value
* Feedback from previous Sprints

A simple priority classification can be used:

``
P1 — Must have / highest value
P2 — Important
P3 — Useful
P4 — Future / optional
```

The team should avoid treating everything as **P1**.

> **If everything is a priority, nothing is a priority.**

---

## 4. Refinement

Backlog items should become clearer before they are selected for a Sprint.

The team may:

* clarify requirements
* split large stories
* add Acceptance Criteria
* identify dependencies
* identify risks
* estimate effort
* remove obsolete items
* reorder priorities

Refinement is continuous rather than a one-time activity.

---

## 5. Selecting Sprint Work

During Sprint Planning, the team selects appropriate high-priority backlog items.

Selection should consider:

``
Priority
   +
Value
   +
Dependencies
   +
Team Capacity
   +
Technical Readiness
        │
        ▼
SPRINT BACKLOG
```

The team should select work that can realistically contribute to the Sprint Goal.

---

## 6. The Backlog Must Evolve

New information will inevitably appear.

For example:

``
User Feedback
      ↓
New Requirement
      ↓
Product Backlog
      ↓
Prioritisation
      ↓
Future Sprint
```

A backlog is therefore a **living product-management instrument**, not a document that is written once and forgotten.

---

# Product Backlog Quality Check

A healthy backlog should have:

* [ ] Clear connection to Product Goals
* [ ] Meaningful priorities
* [ ] Understandable User Stories
* [ ] Acceptance Criteria where appropriate
* [ ] Reasonable story size
* [ ] Visible defects and technical work
* [ ] Dependencies and risks identified where important
* [ ] Obsolete items removed or deprioritised
* [ ] Enough clarity for upcoming Sprint Planning

### Principle

> **The Product Backlog represents what the product may need next — not a promise that everything listed will be built.**

The Product Owner prioritises the **what and why**.

The engineering team collaborates on the **how**.

The Agile process provides the mechanism for turning the highest-value backlog items into **working product increments**.
